AI Gateway v0.2.0

A zero-trust gateway between AI clients and the MCP tools they call, for the fictional Harborline
Supply Co. (all data synthetic). v0.2.0 adds Phase 6: a red-team harness and a per-layer attack
scorecard, and closes the three limits v0.1.0 listed for it. It also carries everything in v0.1.1
(see docs/release-notes/v0.1.1.md), which was cut from v0.1.0 and forward-ported.

What is new
- A per-layer attack scorecard (docs/scorecard.md, docs/scorecard.json, docs/images/scorecard.svg,
  and a section of the README). 31 new attacks, with the four of the acceptance test among 35 files,
  run against the gateway under 17 configurations: every layer on, every layer off, each layer off in
  turn, the weakenable layers only watching, an idealised approver that rejects every write, and the
  three changes below turned back to v0.1.0's behaviour, each alone and all together. Each attack runs as
  a client of its own and is judged by an independent oracle (the databases, a diff of the ticketing
  data, the client's own observation, or the lab upstream's own count of what it executed), never by
  the gateway's own record. Each attack file decides, before any run, what it is for, how its success is
  judged, at what threshold (one leaked customer value for a drip, ten for a bulk export), and which layers
  are expected to stop it; the scorecard reports where a run differed from that prediction and does not
  edit it away. The attacks cover exfiltration through writes (bulk, drip, across sessions), unauthorized
  writes, out-of-scope calls, tool-description poisoning, rug pulls, schema smuggling, canary leakage,
  encoded exfiltration and obfuscated instructions, plus honest runs to measure false positives.
- Reproduce it: LAB_AUTO_APPROVE=yes LAB_MUTABLE_UPSTREAM=yes LAB_FLOOR_OVERRIDE=yes make scorecard
  (a fresh lab Compose project, replay mode, no API key, about 17 minutes once the images are built).
  make scorecard-check is the static check CI runs on every pull request; the full regeneration runs on
  main and nightly. The three switches are the caller's to turn on: the runner sets none of them.
- The three Phase 6 changes to the gateway, each behind a setting so the scorecard shows before and after:
  a value's length and words are counted after underscores, zero-width and every other invisible joiner
  are read as spaces (the model still sees the original; any single token of 64 characters or more is
  judged); long text is cut into units that overlap (unit_overlap_chars); and a result's structured
  content, and the text beside it, must fit the pinned output schema ([schema] validate_results).
- Lab-only tooling, never part of the product: a mutable upstream whose tool definitions change between
  phases (a rug pull, unreviewed tools, a lenient server, a long report with an instruction across the old
  unit boundary), a lab approver that can approve or reject every write, and gateway-admin seed-lab. Each is
  fenced to the lab Compose profile with a switch the caller must turn on, on the internal network with no
  host port, and in no default service or image.
- The simulator's HTTP read timeout is configurable (default 60 s).
- From v0.1.1: the gateway's own request id in every tool result's `_meta` under
  `io.aox.ai-gateway/request_id` (and in an error's `data`), a result's `_meta` that is the gateway's
  alone (an upstream's is dropped), the demo ticket subject in the 09 story corpus with its recording, a
  Postgres healthcheck that asks over TCP (the fix for setup failures on fresh volumes), and one version
  number everywhere, now 0.2.0, with a test that they agree.
- The classifier's recordings cover what the attacks themselves write, including the customer values
  they copy out of what they read (the corpus works the text out from the seed data), so the scorecard
  has no unclassified unit in any column.

Changed behaviour
- Weakening a floor layer (scope or approval) now needs LAB_FLOOR_OVERRIDE=yes in the environment as well
  as allow_floor_override = true in the pipeline file. A file alone can no longer weaken a floor. Compose
  passes the variable through, empty by default.
- A result that fails the pinned output schema, or whose text blocks say anything the structured content
  does not, is refused. [schema] validate_results = false restores v0.1.0.

Known limits (read these before relying on it)
- The scorecard's attacker is a script that does what a planted text says: a compliant model. It does not
  measure how often a real model is talked into it.
- The classifier answers from committed recordings (replay mode, the default). The scorecard shows the
  recorded judgements on this corpus, not a model meeting unseen text. A text with no recording is counted
  as unclassified, never as clean. A deployment must run live.
- Known gaps, shown as successes in the scorecard: egress lets up to nine values leave a client in a window,
  and the drips the scorecard runs land some values before the tally stops the rest; a canary written
  in ROT13 is not matched; an instruction split into pieces shorter than the classifier's minimum is never
  judged. Customer values written backwards are not matched by egress or canary either, but the
  scorecard shows that attack stopped, by the classifier, whose recorded judgement of the one string the
  attack writes flags it: the file's prediction (a success) stands and the difference is listed with its
  reason. It is one recorded judgement of one string, not coverage of reversed exports.
- The unit-overlap change shows no difference on the first long-boundary attack: the classifier flagged both
  fragments of its instruction. A second attack, whose halves are innocent alone, is reported beside it.
- The corpus is small: a rate in the scorecard is a count, not a probability.
- The scorecard's floor-layer columns run under a lab-only override and are labelled so.
- Per-call outcomes can differ from a prediction even where the attack's verdict does not (a drip's second
  write was refused earlier than predicted); only verdicts are compared.
- Unchanged from v0.1.0: argument hashes in records written before the key existed are plain SHA-256; any
  login in the approver role can decide a pending request, including the payload-purge login; the
  dashboard's sign-in redirect takes its scheme from the request URL.

Tested with: Python 3.12, PostgreSQL 17 with pgvector, Node for the dashboard. Details and the review that
found several of the limits above: docs/architecture.md (The red-team harness, The scorecard) and the pull
requests for Phases 6a to 6c.
